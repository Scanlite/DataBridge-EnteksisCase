# DataBridge

DataBridge is a fictional technology service for small and medium-sized businesses that need data moved between tools they already use. This repository is the public landing page and the integration-request flow behind it. It was built as a technical application exercise.

Submitting the form stores a request. It does not connect to Excel, a CRM, or any third-party API.

## Problem

Customer, sales, and operational data often sits in separate spreadsheets, APIs, CRM tools, and reports. Copying that data by hand creates repetitive work, inconsistent records, delayed reporting, and avoidable errors.

## Solution

The site explains that problem and lets a visitor request one of four integration services:

- Excel Automation
- API Integration
- CRM Sync
- Dashboard & Reporting

The implemented product is the page, the form, validation on both sides, and a saved database record. It is not the integrations themselves.

## Features

- Responsive single-page landing page
- Integration request form with name, email, service, and description
- Client-side validation
- Server-side validation with the same rules
- Persistent PostgreSQL storage
- Loading, success, and error states
- Semantic headings, labeled fields, visible focus, and status announcements
- Automated tests for the shared schema and the API

## Architecture / Data Flow

```text
Browser
→ client-side Zod validation
→ POST /api/requests
→ server-side Zod validation
→ Prisma
→ PostgreSQL
→ JSON result
→ success or error UI
```

Client validation is for immediate feedback. The API validates again and is the only path that writes to the database. The success message is shown only after a `201` response that includes `success: true` and a `requestId`.

The server stores `name`, `email`, `service`, and `description`. It sets `status` to `new` and `createdAt` to the database time. Those two values are not accepted from the browser. Email is trimmed and lowercased. The service must be one of `excel_automation`, `api_integration`, `crm_sync`, or `dashboard_reporting`.

A hidden `faxNumber` field is a honeypot. A submission with that field filled in is rejected and is not stored.

## Local Setup

```bash
npm install
```

Copy the environment template and set your own database URL:

```bash
copy .env.example .env
```

On macOS or Linux, use `cp .env.example .env` instead of `copy`.

Edit `.env` and set `DATABASE_URL` to the PostgreSQL connection string from your provider. Then apply the migration and start the app:

```bash
npx prisma migrate deploy
npm run dev
```

`npm install` and `npm run build` already run `prisma generate`. Open [http://localhost:3000](http://localhost:3000).

## Environment Variables

| Name | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Yes, for saving requests | PostgreSQL connection string |

Do not commit `.env`. `.env.example` contains only a placeholder.

The page and the production build can run without `DATABASE_URL`. Saving a request cannot. Until the variable is set and the migration has been applied, a valid form submission returns an error and the page does not show success.

## Database Setup

The Prisma schema is `prisma/schema.prisma`. The model is `IntegrationRequest`:

- `id` — generated by Prisma (`cuid`)
- `name`
- `email`
- `service`
- `description`
- `status` — defaults to `new`
- `createdAt` — defaults to the current timestamp

The initial migration is `prisma/migrations/20261007133000_init_integration_request`.

Apply it with:

```bash
npx prisma migrate deploy
```

Generate the client after schema changes with:

```bash
npx prisma generate
```

`migrate deploy` applies the committed migration. It does not delete data. Do not run `prisma migrate reset` against a database you need to keep.

Persistence against Neon has been checked by hand. The Prisma migration was applied, a real form submission was completed, and the new `IntegrationRequest` row was confirmed in the Neon SQL Editor. No database credential is stored in this repository.

## Validation and Security Decisions

Validation runs in the browser so people can correct a form without a round trip. It runs again on the server because the browser can be bypassed. The server rejects unknown services, malformed JSON, and values outside the length limits.

`status` and `createdAt` are not part of the public schema. The insert sends only the four allowed fields, so a client cannot mark a request as approved or choose its timestamp.

`DATABASE_URL` stays in the environment. The repository does not contain a real connection string. Persistence failures return a generic message. The server log does not include the database error, because that error can contain the connection string.

There is no authentication. The honeypot is the only spam control. There is no CAPTCHA and no rate limiter.

## Known Limitations

- The service is fictional. It has no customers, live integrations, or uptime guarantees.
- There is no admin UI, so saved requests are not listed in the product.
- There are no user accounts and no email notification when a request is saved.
- The form requires JavaScript.
- Spam protection is a hidden field only.
- A fresh checkout still needs its own `DATABASE_URL`. The Neon check above used a local environment file that is not part of the repository.
- The site sends `noindex` so the fictional brand is less likely to appear in search results.

## Deployment

The app is structured for Vercel. `vercel.json` sets the build command to generate the Prisma client, apply migrations, and build Next.js. Set `DATABASE_URL` in the Vercel project before the first deploy. See the manual steps reported with the implementation if this repository has not been deployed yet.

This repository does not include a live URL.
